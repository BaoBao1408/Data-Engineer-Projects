Part 3 — Pipeline Design

The pipeline is designed as a daily batch ELT workflow that ingests operator files, loads them into a centralized analytical warehouse, transforms them into normalized business tables, and produces BI-ready reporting marts every morning.

The current implementation uses:

Python for ingestion and orchestration logic
DuckDB as the analytical warehouse
SQL as the transformation layer
Prefect as the orchestration framework
Pytest + custom quality checks for validation

The final output is stored in:

data/warehouse/warehouse.duckdb

which contains:

raw staging tables
dimensional tables
fact tables
reporting marts
1. High-Level Architecture

The pipeline follows a layered ELT architecture:

Operator CSV Files
        ↓
Ingestion Layer
        ↓
Raw Staging Tables
        ↓
Transformation Layer
        ↓
Dimension + Fact Tables
        ↓
Business Mart
        ↓
Analytics / BI Consumption

The key design decision was using:

ELT instead of traditional ETL.

Raw data is first loaded into the warehouse, then transformed using SQL inside DuckDB. This keeps raw source data immutable and makes debugging, replaying, and auditing much easier.

2. Storage Layer — DuckDB

The warehouse layer is implemented using DuckDB.

The warehouse file:

warehouse.duckdb

stores all analytical layers:

Layer	Purpose
raw_*	landing/staging
dim_*	business entities
fct_*	normalized business events
mart_*	BI-ready aggregates

Example tables:

raw_operator_a
raw_operator_b
raw_clicks

dim_campaigns

fct_subscriptions
fct_billing
fct_clicks

mart_daily_performance
Why DuckDB?

DuckDB was selected because it is:

lightweight
embedded
fast for analytical workloads
excellent for SQL-based transformations
easy to run locally without infrastructure setup

It behaves similarly to cloud analytical warehouses such as:

Snowflake
BigQuery
Redshift

but can run entirely as a local file-based warehouse.

For this scale and use case, DuckDB provides:

vectorized execution
columnar storage
fast aggregations
efficient analytical queries

without requiring distributed infrastructure.

3. Ingestion Layer

The ingestion layer is implemented in:

ingest.py

Its responsibility is:

reading daily operator CSV files
validating structure
standardizing schemas
loading raw data into staging tables

Input files arrive daily in:

data/raw/

Example:

operator_A.csv
operator_B.csv
operator_C.csv
clicks.csv
campaigns.csv
tracking_codes.csv

The ingestion process:

Reads CSV files
Validates row counts and null rates
Standardizes timestamps and column names
Loads data into raw warehouse tables

Example:

operator_A.csv
→ raw_operator_a
Why Python for ingestion?

Python was chosen because:

CSV handling is simple and flexible
schema normalization is easier procedurally
validation logic is straightforward
business-specific parsing rules are easier to maintain

Alternatives considered:

Spark
Airbyte
AWS Glue

These would be more appropriate for:

distributed scale
streaming ingestion
multi-terabyte datasets

For the current workload, Python keeps the solution simpler and easier to debug.

4. Transformation Layer

The transformation layer is implemented in:

transform.py

using SQL executed inside DuckDB.

This layer converts raw operator-specific data into:

normalized dimensions
standardized fact tables
aggregated reporting marts
Main Transformations
Dimension Layer
dim_campaigns

Stores:

partner
service
operator
campaign metadata
Fact Layer
fct_subscriptions
1 row = 1 subscription event

Normalizes:

different operator schemas
attribution logic
tracking identifiers
fct_billing
1 row = 1 billing transaction

Handles:

first bill detection
renewal tracking
revenue calculation
fct_clicks

Stores funnel activity:

clicks
page entries
CTA events
Mart Layer
mart_daily_performance

This is the final BI-ready table.

Grain:

1 row per campaign per day

Metrics include:

subscriptions
first bills
revenue
conversion rates
Why SQL for transformations?

SQL is ideal because:

warehouse transformations are relational
joins and aggregations are central
business logic is easier to audit
analysts can understand the transformations

This approach also aligns with modern analytics engineering practices:

dbt-style transformations
ELT warehouse processing
declarative modeling
5. Orchestration Layer

The pipeline orchestration is implemented using:

Prefect

inside:

pipeline.py

The orchestration flow executes tasks in order:

ingestion
→ transformations
→ mart build
→ quality checks
Why Prefect?

Prefect was selected because it provides:

dependency management
retries
logging
flow visualization
task orchestration

Compared to alternatives:

Tool	Trade-off
Cron	too limited
Airflow	heavier operational overhead
Step Functions	AWS-specific
Prefect	lightweight and Python-native

Prefect fits this project because:

setup is simple
Python integration is strong
orchestration logic is easy to read
6. Idempotency

One important requirement is ensuring the pipeline can safely rerun.

Example problem:

pipeline accidentally runs twice for the same day

The design handles this using:

delete-and-reload logic
deterministic transformations
partition-aware processing

Before loading a run date, the pipeline removes existing rows for that partition.

This guarantees:

no duplicate subscriptions
no double-counted revenue
consistent marts after reruns
7. Handling Late or Bad Files

The design anticipates operational issues.

Late-arriving files

If a file arrives late:

the run can be replayed using a specific processing date
historical partitions can be rebuilt

Example:

python pipeline.py --date 2026-01-15

This supports:

backfills
reruns
replayability
Bad data quality

The pipeline includes validation logic:

row count thresholds
null-rate checks
malformed tracking code detection

Example anomaly:

tracking_code length > 3

These records are:

logged
flagged
excluded from attribution logic

without crashing the entire pipeline.

Partial failures

If one task fails:

Prefect marks the flow failed
downstream tasks do not execute
logs capture the failing step

This prevents partially updated marts.

8. Monitoring and Observability

The pipeline includes:

structured logging
pipeline run tracking
automated validation checks

Example validation rules:

revenue must not be negative
subscriptions cannot exceed clicks
mart tables cannot be empty

Pipeline metadata is stored in:

pipeline_runs

This enables:

auditability
run history tracking
operational monitoring
9. Why This Design Works Well

This architecture works well because it cleanly separates responsibilities:

Layer	Responsibility
ingestion	raw data loading
warehouse	centralized analytical storage
transformation	business normalization
mart	BI consumption
orchestration	scheduling + dependency management

The design is:

modular
testable
replayable
debuggable
warehouse-centric
10. Future Improvements

If the system needed to scale further, the next evolution would likely be:

Current	Future
DuckDB	Redshift / Snowflake
local CSV	S3 data lake
Prefect local	Airflow / Step Functions
SQL scripts	dbt
local execution	containerized deployment

The current architecture was intentionally designed so these upgrades could happen incrementally without changing the core modeling approach.
